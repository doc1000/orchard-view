1. Purpose

The visual search tool is a structured culling interface for large document corpora organized into hierarchical trees. It is not a keyword search engine. It is an exploration and discernment tool — the user navigates a cultivated taxonomy to narrow, filter, and commit to a working set of documents across multiple search cycles.

Three synchronized views — Domain Tree, Function Tree, and Treemap — are lenses on the same underlying document scope. A query bar and per-node / per-document polarity controls all write into a single Decision Ledger. Every view reads its state from that ledger. Views never own independent filtering state.

The design philosophy is trading interface clarity: fast, decisive actions over large, deep document spaces. Depth of provenance is available but not forced on the user. The goal is confident, rapid narrowing — not surgical precision over every edge case.

3. State Model

Five stores. One source of truth for document scope.

CORPUS
Immutable universe. All available documents. Changes only on data load/refresh.
BASE
Committed selection. Starts as CORPUS. Advances on Go.
DECISION LEDGER
Ordered, timestamped list of all polarity actions from any view.
WORKING SCOPE
Derived: evaluate(BASE, LEDGER). Recomputed on every ledger change.
HOPPER
Independent persistent collection. Survives Go, Undo, and Reset.
CORE PRINCIPLE
Views emit decisions into the ledger and render from the derived working scope. Views never own or manage filtering state independently.

State Transition Flow

CORPUS → session start → BASE = CORPUS
BASE + decisions → WORKING SCOPE (diff view)
WORKING SCOPE → GO (commit) → BASE = WORKING SCOPE · ledger → history · query bar cleared
UNDO → removes last ledger entry · recomputes scope · can undo past Go (with confirmation)
RESET → BASE = CORPUS · ledger cleared · all views return to full state
WORKING SCOPE docs → ADD → HOPPER · does not affect BASE or scope

5. Decision Ledger

Every polarity action from any view writes a timestamped entry. The ledger is the single source of truth for all active decisions. It is evaluated in full on every scope recompute. After a Go, the active ledger is cleared and archived as session history. A dropdown on the Conditions row provides access to prior ledger states.

Ledger Entry Shape

{
  ts:          number,          // epoch ms — used for last-action-wins at equal specificity
  source:      "query" | "domain_tree" | "function_tree" | "treemap" | "results_list",
  target_type: "term" | "node" | "document",
  target_id:   string,         // node_id or doc_id or query term string
  polarity:    "include" | "exclude" | "neutral"
}

Example Ledger

t+0001 query term: "fintech" include
t+0042 domain_tree node: health-wellness exclude
t+0087 domain_tree node: nutrition-diet include
t+0121 results_list doc: doc_id_00447 exclude

6. Scope Evaluation Rules

Precedence Hierarchy

1 Document decision explicit right-click on a result — highest specificity, always wins
2 Child node decision more specific node overrides its parent's broadcast
3 Parent node decision broadcasts downward to all descendants by default
4 Query inference lowest specificity — explicit node/doc action overrides
SETTLED DECISION
At equal specificity: last timestamp wins. If Domain includes Health and Function later excludes a doc that lives under Health, that doc is excluded. This is intentional — the user made an active decision. The interface should reflect what was last clicked. Users are responsible for checking both trees when using multiple views simultaneously.

Broadcast Rule

A polarity decision on a node applies to all descendant nodes and documents by default. A more-specific decision on a child overrides the parent broadcast for that child's subtree.

Example: Exclude Health & Wellness → all children fall out of scope. Then include Nutrition & Diet → Nutrition's documents return. The Health parent remains excluded for all other children.

Cross-Tree Conflicts

Domain Tree and Function Tree nodes do not map 1:1. A document can appear under an included Domain node and an excluded Function node. Resolution: last action timestamp wins. If the Function exclusion is newer, the document is excluded. No hidden priority between trees — recency is the only tiebreaker.

Consequence: a node in one tree may display as partially in-scope because documents it contains have been excluded by the other tree. The node count (W / B) will reflect this accurately.

7. Query Matching

Unquoted Terms

Fuzzy / token match against document content and node labels. If a node label matches, the entire branch below that node stays in scope. This is intentional — we are searching structures, not just documents. Selecting a node by query is equivalent to a node-level include action.

Quoted Phrases

"exact phrase" — exact string match on document content only. No branch inheritance from matching a node label. A quoted phrase must appear literally in a document for that document to remain in scope.

Negative Terms

-term or -"phrase" — excludes matching documents or branches. Follows the same branch inheritance rules as positive unquoted / quoted matching.

OR Groups

Terms separated by or form separate groups. Within a group, terms combine as AND. Between groups, OR. The Conditions row should display parsed groups as visually distinct blocks so the user can verify the interpretation. 

"beach vacation" -hawaii  OR  remote ML fintech jobs

GROUP 1: INCLUDE exact "beach vacation"  AND  EXCLUDE term hawaii
OR
GROUP 2: INCLUDE remote  AND  INCLUDE ML  AND  INCLUDE fintech  AND  INCLUDE jobs

After Go

Query text is removed from the bar. A clickable history dropdown preserves all prior queries in session order.

8. Visual States

Node States (Trees & Treemap)

Neutral
No active decision. All documents in BASE remain in scope.
Included ✓
Explicit positive polarity on this node. Branch highlighted green. Transmitted to children.
Excluded ✗
Explicit exclusion, OR zero documents remain (empty before Go = red). Branch red. Transmitted to children.
Partial
Node has both in-scope and out-of-scope children. Count W/B shows the split.
SETTLED DECISION
Node color is based on the node's own polarity decision, transmitted downward. There are no mixed-color nodes. A parent excluded turns red; if a child is specifically included, that child turns green. No badges or overlapping states — fast, clear, tradeable.

Before Go: Diff View

While decisions are active but uncommitted, all views operate in diff mode. In-scope documents display normally; out-of-scope documents display in red / dimmed in the Results List. Nodes with zero remaining documents display red (giving the user the opportunity to adjust polarity before committing). This is the "branch on the staging area" state.

After Go: Clean Slate

All polarity coloring clears. The new BASE is the committed scope. Trees show only nodes with documents. Empty nodes are hidden. Counts reset to the new BASE. No visual trace of prior decisions remains in the main views (history available via Conditions dropdown).

Results List

  • In-scope documents appear first, full opacity.
  • Out-of-scope documents appear below, dimmed / red, with a "Show excluded" toggle.
  • Count display: 138 in scope · 709 excluded
  • Right-click on any document: cycle polarity — neutral → include → exclude → neutral.

Hopper

Persistent strip at the bottom. Shows saved document chips. Has its own export and clear controls independent of all search state.

9. Controls Reference

CONTROL ACTION STATE EFFECT
GO Commit working scope BASE ← WORKING SCOPE · LEDGER → history · query cleared · blocked if scope=0
UNDO Remove last ledger entry; re-evaluate Scope recomputed. Can undo past a Go (shows "Undo GO?" confirmation beneath button). Undo history persists for session.
RESET Return to full corpus BASE ← CORPUS · LEDGER cleared · WORKING SCOPE ← CORPUS · HOPPER untouched
PARSE Parse query bar into conditions Adds parsed entries to LEDGER · scope recomputed · conditions shown in row below query bar
PRUNE Remove currently out-of-scope entries from view Visual-only collapse of excluded nodes in trees
ADD → HOPPER Save in-scope docs to hopper HOPPER receives current WORKING SCOPE docs · does not affect BASE or scope
Tree click Cycle node polarity (neutral → include → exclude) Writes ledger entry · WORKING SCOPE recomputed · all views update

10. Settled Design Decisions

DECISION 1 — RESET BEHAVIOR
Reset returns BASE = CORPUS. There is no separate "clear decisions" operation — that is covered by Undo stepping back through the ledger. The Undo button can step back past a Go commit (with a visible "Undo GO?" confirmation beneath the button for quick confirmation). The user can then inspect and modify prior decisions before committing again.
DECISION 2 — EQUAL SPECIFICITY CONFLICT
Last action wins. At equal specificity (e.g., two node-level decisions from different trees covering the same document), the most recently timestamped ledger entry wins. No hidden hierarchy between trees. User intent expressed through recency. Users accept responsibility for checking both trees in complex multi-tree workflows.
DECISION 3 — NODE COLOR MODEL
Single color per node based on its own explicit decision, transmitted to children. No mixed/multi-color nodes. A green parent with a red child is clear: the child has a more specific decision that overrides. Badges are avoided — the interface is optimized for fast scanning over large taxonomies.
DECISION 4 — NO HARD/SOFT INCLUSION DISTINCTION
A document is in scope or it is not. Whether it matched via direct document match or via node label match (branch preservation) makes no difference to scope membership. Downstream specific decisions may still override branch membership. No intermediate states required.
DECISION 5 — QUERY CLEARED ON GO
Query bar clears after Go. The active bar is for uncommitted working decisions only. A history dropdown on the query bar preserves all prior queries in session order. Similarly, the Conditions row has a dropdown for prior ledger states.
DECISION 6 — GO BLOCKED AT ZERO SCOPE
Go is disabled (button grayed, no action) when WORKING SCOPE is empty. Prevents accidental zero-document commits. User must adjust decisions before committing.
DECISION 7 — EMPTY NODES BEFORE / AFTER GO
Before Go: empty nodes are displayed in red — the user sees the full impact of their decisions and can reverse them. After Go: empty nodes are hidden by default (the new BASE has no documents there to show).
DECISION 8 — HOPPER INDEPENDENCE
The Hopper receives documents from any number of search cycles. It has its own save, export, and clear controls. Clearing the Hopper has no effect on BASE, WORKING SCOPE, or the DECISION LEDGER. The Hopper is the cross-cycle collection mechanism.
DECISION 9 — TREEMAP / TREE NODE IDENTITY
Treemap nodes and tree nodes share the same node_id namespace. A polarity decision on a treemap rectangle writes the same ledger entry as clicking the equivalent tree node. The views are lenses on the same structure, not separate hierarchies.
DECISION 10 — DOCUMENT PROVENANCE / INSPECTION
Full decision provenance (which ledger entries affected a document and why) is available in session ledger history. It is not surfaced as persistent hover annotation on the main interface — that would add clutter. The interface prioritizes fast, clear decisions. Detailed inspection is available on demand.

11. Manual Acceptance Tests

T1 Parent exclusion with child restoration
  1. Start with full corpus.
  2. Exclude Health & Wellness in Domain Tree.
  3. Confirm every document under it is out of scope — red in Results, red in both trees, reflected in Treemap.
  4. Include Nutrition & Diet (child of Health).
  5. Confirm Nutrition documents return to scope. Health & Wellness parent shows partial (yellow count discrepancy W/B). Nutrition node shows green.
  6. Verify Function Tree nodes that contain the same Nutrition documents reflect the same in-scope count.
  7. Press Go. Confirm committed scope matches working scope exactly. All polarity coloring clears. Empty nodes hidden.
T2 Parent inclusion with child exclusion
  1. Include Work & Careers in Domain Tree. Confirm documents outside that branch fall out of scope.
  2. Exclude Finance & Fintech (child). Confirm those documents are removed even though parent is included.
  3. Verify Domain Tree, Function Tree, Treemap, and Results List all contain identical document IDs.
  4. Press Go. Verify committed BASE counts match.
T3 Cross-tree conflict (last action wins)
  1. Include a Domain node containing Document A.
  2. Exclude a Function node also containing Document A. Confirm Document A is excluded (Function action is newer).
  3. Now include Document A directly via right-click in Results List. Confirm it returns (document decision is most specific).
  4. Press Go. Document A is in committed BASE.
T4 Query plus polarity — multi-source commit
  1. Search for fintech. Parse. Confirm working scope narrows across all views.
  2. Explicitly exclude one matching tree branch. Confirm those docs go red.
  3. Explicitly include one document via Results List right-click.
  4. Press Go. Confirm committed set includes the directly-included document and excludes the excluded branch — all three actions accounted for.
T5 Exact phrase vs. fuzzy
  1. Search "machine learning". Confirm only documents containing that exact phrase survive (no branch inheritance from a node labeled "Machine Learning").
  2. Clear. Search machine learning (unquoted). Confirm documents matching either token survive, AND that a node labeled "Machine Learning" keeps its entire branch in scope.
  3. Verify the Conditions row shows the distinction between the two query types.
T6 Undo past Go
  1. Start at 847. Narrow to 138. Press Go.
  2. Further narrow from 138 to 30. Press Undo repeatedly — confirm ledger entries are reversed one at a time.
  3. Undo past the Go commit. Confirm "Undo GO?" prompt appears beneath Undo button. Confirm. Scope returns to 138 with prior decisions restored and visible.
  4. Modify a decision. Re-commit with Go. Hopper contents survived throughout.
T7 Reset vs. Undo — understanding the difference
  1. Start at 847. Narrow to 138. Press Go.
  2. Narrow from 138 to 30.
  3. Press Reset. Confirm: BASE = CORPUS (847 docs), LEDGER cleared, WORKING SCOPE = CORPUS. Not 138.
  4. Confirm Hopper survived. Confirm query history dropdown still shows prior queries.
T8 Multi-cycle Hopper
  1. First search cycle: narrow to fintech docs, Add selected docs to Hopper. Press Go.
  2. Second search cycle: narrow to ML docs, Add those to Hopper.
  3. Confirm Hopper holds docs from both cycles.
  4. Reset. Confirm Hopper still holds all saved docs. Clearing the Hopper has no effect on search scope.
T9 Zero-result guard
  1. Create contradictory conditions that yield 0 documents in WORKING SCOPE.
  2. Confirm Go button is disabled / grayed out. Confirm count shows 0 in scope.
  3. Confirm all nodes are red. Confirm user can still see and remove decisions causing the conflict.
  4. Remove one conflicting decision. Confirm Go re-enables when scope > 0.
